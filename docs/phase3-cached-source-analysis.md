# 第3段階: 保存済みHTMLの再解析結果

## 目的と安全範囲

`scraper/html_cache` に既に保存されていた DokkanInfo のHTMLだけを読み、現行の敵データで失われている情報をどこまで復元できるか調べた。

- DokkanInfo への新しいアクセス: **0回**
- Bot対策やアクセス制限の回避: **なし**
- `scraper/all_enemies.json` の上書き: **なし**
- `dokkan_calc_final.js` の埋め込みデータの上書き: **なし**
- 解析元キャッシュの取得日時: `2026-02-23T08:11:11.385Z`
- 解析結果: `artifacts/phase3/cached-source-analysis.json`（約27KBの集計だけ。HTML本体の複製はしていない）

この調査は「保存時点のHTMLを技術的に再解析できるか」の確認であり、DokkanInfoへの自動取得を再開してよいという判断ではない。

## 結論

保存HTMLには、現行JSONよりかなり多くの情報が残っている。特に、イベントID、ステージID、カード参照ID、HP、DEF、ダメージ軽減率、最大攻撃回数、必殺技の表示値、敵スキルID・説明、全体攻撃値の復元が可能だった。

一方、HTML上の並びだけでは、複数の敵行が「連続する変身段階」なのか「同時に出る複数の敵」なのかを全ステージで安全に断定できない。また、細かい行動位置が表示されているのは一部だけである。したがって、保存HTMLをそのまま本番データへ変換するのではなく、まず別スキーマへ保存し、曖昧な箇所を明示してから移行するのが安全である。

## 現行4,245件との照合

現行JSONは647ステージ、4,245ボスである。名前、超/極、属性、ATK、必殺ダメージ、並び順を使って、保存HTMLのステージと照合した。

| 照合方法 | ステージ | ボス |
|---|---:|---:|
| 全項目が一致する候補あり | 622 / 647（96.14%） | 3,880 / 4,245（91.40%） |
| 候補を1ステージに確定 | 620 / 647（95.83%） | 3,828 / 4,245（90.18%） |
| 超/極の差だけ無視 | 635 / 647（98.15%） | 4,051 / 4,245（95.43%） |
| 超/極と必殺表示値の差を無視し、名前・属性・ATK列を比較 | 646 / 647（99.85%） | 4,243 / 4,245（99.95%） |

最後の緩い照合は「同じ敵だと確定した」という意味ではなく、差の原因を絞るための診断である。名前・イベント名だけなら全647ステージに候補があるが、同名ステージが多いため95ステージは複数候補になる。

厳密一致した3,880ボスについては、対応するカードIDを欠損なく得られた。曖昧な例は、現行データに2回存在する「超激戦BOSSラッシュ2」で、保存HTML側にも `7010024` と `7010025` の同一内容候補があるケースである。

保存HTML801ステージのうち、厳密一致に使われなかった候補は179ある。これには現行JSONが採用しなかったステージ、別難易度、同一表示名の候補、戦闘ステータスを表示しないプレビューが含まれるため、「179ステージが欠落している」とはまだ断定できない。

## 明確に見つかった旧解析の問題

1. **中立アイコンを極としていた。** `cha_type_icon_00`〜`04` は超でも極でもない中立表示だが、旧parserは超でなければ初期値の極を使用した。名前・属性・ATK列で一意に対応できた4,061ボス中、138件が「HTMLは中立、現行JSONは極」だった。キャッシュ全体では中立行が443件ある。

2. **表示のない必殺を3倍として作っていた。** 一意に比較できた4,061ボス中17件で、HTMLには必殺ダメージがないのに現行データには `ATK × 3` が作られていた。キャッシュ全体では、ATKがあるが必殺ダメージ表示がない行が95件ある。表示なしと3倍を同じ意味にしてはいけない。

3. **スピードバトル予選に不自然なATK 20/30が作られている。** 保存HTMLの「予選ステージ」にはカード候補19行があるが、いずれも戦闘ステータスが表示されていない。現行JSONにはベジットATK 20、超ベジットATK 30の2ボスがある。旧parserが別用途の数字をATKとして拾った可能性が非常に高く、646/647ステージの緩い照合でも一致しない唯一のステージだった。

4. **AOEが失われていた。** 旧正規表現は「エリアダメージ 1: 数値」の途中にある `1` を適切に扱えず、現行データではAOE値が0になっている。保存HTMLからは65 encounterについて、1体目と2体目以降を分けて復元できた。

5. **DEF等を捨てていた。** 保存HTMLでは戦闘用4,673行すべてにDEFがあるが、現行JSONのボス形式にはDEF、HP、ダメージ軽減率、最大攻撃回数、skill ID、encounter情報がない。

なお、非常に大きい必殺倍率は機械的に異常値として削除してはいけない。例えば保存HTMLにはATK 58,000、必殺ダメージ58,057,420（派生倍率1000.99）の特殊なカウントダウン攻撃が実在する。まず元表示を残し、用途を別途分類する。

## 重複と曖昧性

- stage ID 801件と構造的な敵出現ID 5,032件に重複はなかった。
- card IDは同じカードが複数ステージで再利用されるため、2,285回分の再出現がある。card IDだけを敵出現の一意IDにしてはいけない。
- 同じステージ内で名前・属性・ATK・必殺値が同じ敵が繰り返されるケースが615行分ある。クローン等では正常な繰り返しである。
- ステージの敵列だけを見ると、116種類の列が複数ステージで再利用され、最多は44ステージで同一だった。イベント名や表示順だけでなく、source/event ID/stage IDを必ず組み合わせる。
- 1 encounterに複数敵行を持つものは1,120件、最多150行だった。バトルロードの同時出現と連続変身を同じ規則でphase扱いしない。

## 将来のスキーマ案

AI行動表の順番は遭遇全体の通し番号ではない。保存HTMLの全100グループで表示順は
1始まりであり、複数の敵が行動表を持つ13グループでは番号が1から繰り返される。
将来データでは表ごとの`sequenceIndex`、元表示の`sourceOrder`、`enemyOrder`、
`slot`を分けて保存する。

IDは外部の不透明な識別子として文字列で保存し、数値の桁を分解して意味を推測しない。最小の一意キーは次の組み合わせを推奨する。

- event: `source + region + eventId`
- stage: `source + region + eventId + stageId`
- enemy occurrence: `source + region + eventId + stageId + encounterIndex + orderInEncounter`
- enemy entity参照: `cardId` と `thumbId` の両方（出現IDには使わない）

概略は次の形が安全である。

```json
{
  "schemaVersion": 1,
  "source": {
    "name": "dokkaninfo-cache",
    "region": "jpnja",
    "downloadedAt": "...",
    "parserVersion": "...",
    "sourceFile": "..."
  },
  "event": { "eventId": "701", "title": "..." },
  "stage": {
    "stageId": "7010105",
    "name": "...",
    "encounters": [
      {
        "encounterIndex": 0,
        "layoutKind": "unknown",
        "enemies": [
          {
            "orderInEncounter": 0,
            "cardId": "1014481",
            "thumbId": "1014480",
            "name": "孫悟空(GT)",
            "alignment": "super",
            "type": "str",
            "rawTypeIconId": 13,
            "stats": { "hp": 1859000, "atk": 47590, "def": 5900, "damageReductionPercent": 45, "maxAttacksPerTurn": 3 },
            "superAttack": { "damage": 118975, "multiplierDerived": 2.5, "description": "...", "effects": [] },
            "skills": [{ "id": "6450", "description": "...", "probabilityPercent": null, "icons": [] }]
          }
        ],
        "renderedAiActions": [],
        "areaDamage": null
      }
    ]
  }
}
```

重要なルールは次のとおり。

- `0`、`null`（表示なし）、未解析を別の状態として保持する。
- `alignment` は `super | extreme | neutral | unknown` とする。
- 必殺倍率だけでなく、元のATKと必殺ダメージを保存する。
- skill原文、skill ID、アイコン、AIのraw textを残し、後から解析規則を改善できるようにする。
- 自動抽出値にはsource file、parser version、警告を付ける。
- `layoutKind` は最初は `unknown` とし、根拠があるステージだけ `sequential` / `simultaneous` / `mixed` にする。
- AOEはHTML上でencounterに属するため、根拠なく特定の敵1体へ付け替えない。
