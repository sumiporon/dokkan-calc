# 第3段階: 将来構成と敵データ設計の再評価

確認日: 2026-08-21（JST）

## 結論

Vite、TypeScript、敵JSON分離は、いずれも第4段階以降では引き続き有力である。ただし、3つを同時に導入して巨大なJavaScript全体を書き換える方法は採らない。

今回の調査で、難しさの中心は「ビルドツールがないこと」よりも、次の3点だと分かった。

1. 計算仕様に確定部分と未確定部分が混在している。
2. 約5.1MB・16万行のJavaScriptに、画面処理と4,245体分の敵データが同居している。
3. 現行敵データはID、DEF、skill、AOEなどを失っており、名前と並びだけでは安全に移行できない。

そのため、第4段階ではまず「データの契約」と「互換アダプター」を作り、その後にViteとTypeScriptを小さな新規モジュールから導入するのが最も安全である。

## 今回実施した小さな構造改善

`src/calculation-core.js` を追加し、ブラウザとNode.jsテストの両方から同じ純粋関数を呼べるようにした。これは移行途中の橋渡しであり、ViteやTypeScriptを前提にしていない。

- 画面DOMを触らず、数値を受け取って結果を返す。
- メインカード、一覧、スクリーンショット用プレビューが同じ計算を使う。
- 旧挙動を残すDEF部分には `LegacyCompatible` という名前を付け、ゲーム仕様として確定した関数と誤認しないようにした。
- ターン開始時枠と被弾後枠を分離した。
- 後から計算段階や整数化位置を差し替えられる境界を作った。

巨大JavaScriptの全面分割は行っていない。

## 将来敵データの設計原則

形式案は `schemas/enemy-data-v1.draft.schema.json`、非本番の最小例は `tests/fixtures/future/enemy-data-v1.example.json` に置いた。例は実在サイトや実在敵と混同しない完全な架空データである。どちらも設計・検証用であり、現行アプリはまだ読み込まない。

### 1. 取得元の事実とアプリ用の派生値を分ける

例えば「画面に表示された必殺ダメージ」と「ATKから割り戻した必殺倍率」は同じ信頼度ではない。元の数値を `displayedDamage`、計算した値を `derivedMultiplier` として別々に残す。

### 2. IDを名前の代わりに使う

敵の出現位置を表す最小キーは次の組み合わせとする。

```text
source + region + eventId + stageId + encounterIndex + orderInEncounter
```

`cardId` は同じキャラクターが別ステージでも使われるため、単独では出現IDにならない。保存HTMLでは `cardId` と画像の `thumbId` が5,006行で異なるため、両方を保持する。

### 3. 不明を0で埋めない

- `0`: 取得元で0と確認できた。
- `null`: 数値を補完しない。
- フィールドなし: スキーマ上その概念が対象外。

`null`の場合は `fieldStates` に `source-not-rendered`、`not-applicable`、`parse-failed`、`unconfirmed` のどれかと理由を記録する。この区別により、「必殺表示なし」を3倍必殺として作るような誤補完を防ぐ。

### 4. 条件は共通のeffect配列で表す

ターン、被弾、HP、登場、必殺後、会心などを別々の場当たり的な名前で増やさず、次を持つeffectとして保存する。

```text
発動条件 / 対象 / 演算 / 値 / 上限 / 計算枠 / 根拠 / 確度
```

ただし、会心とAOEは誤計算時の影響が大きいため、検索・検証しやすい専用項目も持つ。

### 5. 生テキストを捨てない

skill ID、元の説明文、アイコン、AI行動のraw text、取得元ファイルを残す。parserを改善したときに外部サイトへ再アクセスせず再解析できる。

### 6. 手動補正を本体へ混ぜない

手動補正は、安定した敵出現ID、敵の中での対象field、補正前の期待値、元dataset IDとdigest、変更値、理由、根拠URL、確認日、確認者を独立配列に記録する。配列番号を含むJSON Pointerで敵を指定すると、再生成時の並び替えで別の敵へ補正がずれるため使用しない。元データの値を黙って上書きしない。

## 主な階層

```text
dataset
├─ sourceSnapshot
└─ events[]
   └─ stages[]
      └─ encounters[]
         ├─ enemies[]
         │  ├─ identity
         │  ├─ stats
         │  ├─ attacks
         │  ├─ passiveEffects
         │  └─ critical
         ├─ aiActions[]
         └─ areaAttacks[]
```

`aiActions` は遭遇全体で1本の連番にはしない。保存HTMLでは敵ごとの表がそれぞれ
「アクション1」から始まるため、`sequenceIndex` で表を分け、表示された1始まりの
`sourceOrder` と `slot` をそのまま保持する。画面側で0始まりが必要なら読み込み時に
変換し、元データを上書きしない。

`encounter` は、取得元HTMLのひとまとまりを意味する。現時点では、それが連続変身なのか同時出現なのかを常に断定できないため、`layoutKind` の初期値を `unknown` にする。根拠がある場合だけ `sequential`、`simultaneous`、`mixed` を設定する。

必殺後効果は各必殺の `effects` に持たせ、敵全体の `passiveEffects` と混同しない。必殺だけ会心になる敵は各必殺の `criticalOverride` で表し、通常攻撃まで会心扱いしない。AOEは保存HTMLの元値である `maxPerTurn`、`firstTargetDamage`、`additionalTargetDamage` を先に保存し、倍率は派生値として分離する。

draft schemaのテストは項目名を見るだけではなく、AJVでexample全体を検証する。さらにJSON Schemaだけでは表しにくい、複合出現ID、ID重複、出現順、派生必殺倍率、HP範囲、null理由、手動補正の元値・digest、主要件数の急減を意味検査する。

## Viteの再評価

判定: **第4段階以降で推奨。ただし最初の作業にはしない。**

利点:

- 小さなモジュールを通常の `import` / `export` で管理できる。
- 開発用サーバー、ビルド、GitHub Pages用の相対パスを一定の方法で扱える。
- TypeScriptやJSON検証を後から自然に追加できる。
- 画面用コードとテスト用コードで同じモジュールを使いやすい。

注意点:

- Viteを入れただけでは計算式やデータ欠落は直らない。
- 現在の静的HTMLは簡単に復旧できるため、移行中も旧起動方法を残す。
- Pagesの公開方法変更は大きな方針変更なので、実行前に別途説明する。

## TypeScriptの再評価

判定: **新規モジュールと新敵データ形式から段階導入を推奨。巨大JSの一括変換は非推奨。**

今回のように、`crit rate` と `crit ATK multiplier`、`null` と `0`、`cardId` と出現IDを混同すると計算が壊れる。TypeScriptはこの種の取り違えを編集時に検出しやすいため、敵データ正規化層と計算入力で特に効果が高い。

一方、16万行を一度に `.ts` 化すると大量の型エラーと画面回帰が同時発生する。第4段階では `calculation`、`enemy-schema`、`enemy-adapter` など新規の境界だけをstrict TypeScriptにし、旧画面コードは当面JavaScriptから呼び出す。

## 敵JSON分離の再評価

判定: **引き続き推奨。ただし候補データの検証と互換アダプターが先。**

分離すると、アプリコードの差分と4,245体分のデータ差分を別々に確認できる。更新時の誤削除や属性変化もレビューしやすい。約5.1MBの巨大JSを小さくできる効果も大きい。

ただし、第3段階では次を変えていない。

- `scraper/all_enemies.json`
- `dokkan_calc_final.js` 内の現行埋め込みデータ
- アプリが読むデータ経路
- localStorage形式

第4段階では、まず非本番の新形式候補を生成し、現行形式へ戻す読み取り専用アダプターを作る。その出力が現行4,245件と意図した差だけになることを確認してから、アプリの読み込み先を切り替える。

## 推奨する第4段階の順序

1. 乱数の表示仕様について所有者の選択を確定する。
2. draft schemaを実データ数十件で試し、連続phase・同時出現・AOE・会心の代表例を固定する。
3. 保存HTMLから非本番の候補JSONを生成し、出典と警告を付ける。
4. 新形式から現行形式へ変換する互換アダプターと意味的差分レポートを作る。
5. 中立属性、誤補完必殺、AOEなどを個別レビューする。自動で本番採用しない。
6. Viteを導入しても旧静的版を並行起動できる状態を作る。
7. 新規の計算・データ層だけTypeScriptにする。
8. 全テストとブラウザ比較後、別承認で敵JSON読込と公開方法を切り替える。

この順序なら、技術変更、データ変更、公開変更を一度に重ねず、問題が起きた箇所を初心者でも追いやすい。
